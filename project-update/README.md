# 项目收尾（project-update）

项目收尾流程：更新工作日志、项目状态与 README；存在 git 仓库时，依次执行自检、敏感内容扫描、提交与推送。

## 功能定位

一次开发完成后，耗时往往不在编码环节，而在收尾工作：补充日志、更新状态、执行自检、确认无不当内容进入提交、撰写提交信息、推送远端。

本 skill 将该流程整合为单条流水线，执行过程不中断询问，仅在明确的停止条件下中止。

## 核心机制

### 一、按仓库状态分级处理

| 状态 | 执行内容 |
|---|---|
| 有仓库，远端归属自身 | 完整流程：文档 + 自检 + 敏感扫描 + 提交 + 推送 |
| 有仓库，无远端 | 文档 + 自检 + 敏感扫描 + **提交，不推送** |
| 有仓库，远端归属他人 | **不适用本 skill**，告知后终止 |
| **无仓库** | **仅执行文档与自检**，并在汇报中注明 |

**无仓库属正常情形，非异常路径。** 相当比例的项目不应建立仓库，补充工作日志是其中价值最高的部分，不应因缺少仓库而整体跳过。

同理：**不得代为执行 `git init`。** 是否建立仓库涉及公开范围、账号归属、`.gitignore` 设计等决策，不属于收尾流程的职责范围。

### 二、敏感内容扫描

扫描规则**以各仓库自身的 `.gitignore` 为唯一依据**，不另行建立白名单或黑名单，仅检查其遗漏项。

**已验证的失效情形**：某一轮扫描报告工作日志命中 `ghp_` 与 `github_pat_`，经核查为误报。命中来源为日志中如下一行：

> 敏感串扫描：`ghp_` / `github_pat_` / `sk-` / `AKIA` / 私钥 / `Bearer` —— 零命中

**用于记录"已扫描哪些模式"的说明文字，其本身构成模式名的匹配来源。**

**处置方式**：每条模式必须附带**尾部长度限定**。真实 token 形如 `ghp_` 加 36 位字符；文档中提及模式名时其后紧跟反引号、空格或斜杠，长度不足，因而不会触发。

```bash
git grep -n -I -E \
  "sk-[A-Za-z0-9]{20}|ghp_[A-Za-z0-9]{36}|github_pat_[A-Za-z0-9_]{60,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY|Bearer [A-Za-z0-9_.-]{30}|password *="
```

配套规则：**命中后先检查尾部**。前缀之后若非连续 token 字符，判定为误报，以单行注明即可，不中止流程。

## 停止条件

命中以下情形时中止，不自行决断：自检失败；扫描到疑似凭据；`origin` 非自身仓库；需强制推送；缺少工作日志文件；本地分支与远端分叉。

## 执行要求

**自检须沿用项目既有方式，不得新设一套。** 优先检查项目已有的自检入口（`Cargo.toml`、`package.json`、`Makefile`、项目自带核对脚本），执行既有方式。**若均不存在则跳过，并在汇报中明确说明"无自检可执行"**——省略此项会导致阅读者默认已完成验证。

**仅推送自有仓库。** 项目目录中常包含第三方仓库（依赖包、克隆的源码），此类仓库虽具写权限但不属于自身，为后果最严重的常见错误。

## 触发方式

```
"更新项目"    "更新一下项目"    "项目收尾"
```
