# 更新项目（收尾一条龙）

把一个项目从"本地改完了"推到"远端上是新的"，顺带把工作文档补齐。

**默认作用对象 = 当前会话所在的项目**；用户点名了别的项目就换过去。

**这个 skill 不只是给 git 项目用的。** 很多项目**压根没建库**。没库的就**只更新文档**，git 那一整段自然跳过——**不要因为它没库就整个 skill 不干活**。

**全程自动，不设确认闸门。** 只在下面「硬停清单」命中时停下来报给人。

---

## 第〇步：先判仓库状态（决定后面走哪条路）

从当前目录**向上找 `.git`**，按结果分四档：

| 状态 | 做什么 |
|---|---|
| **① 有库 + 远端是自己的** | **全套**：文档 + 自检 + 敏感扫描 + commit + push |
| **② 有库 + 无远端** | 文档 + 自检 + 敏感扫描 + **commit，不 push**。汇报里注明"无远端" |
| **③ 有库 + 远端是别人的** | **整个 skill 不适用**。告诉用户"这是第三方仓库"就结束 |
| **④ 没建库** | **只做文档 + 自检**。跳过敏感扫描 / commit / push；汇报里注明"未建库" |

两点容易搞错：

1. **仓库常嵌在项目子目录里**——子目录才是仓库根，外层只是项目壳。在错误的层跑 git 命令会报"不是仓库"。
2. **找不到 `.git` 不是出错**，那就是第 ④ 档，继续往下走，**别停也别去问**。

第 ④ 档往往占多数，**不是异常路径**。没库不代表这活白跑——**补工作日志才是最有价值的那一半**。

---

## 硬停清单（命中即停，不自行决断）

| 情况 | 怎么办 |
|---|---|
| 自检红 | 停。不 commit。**把失败输出原文贴给人看** |
| 扫到疑似凭据 / 不该外发的正文 / 单个 >5MB 的新文件 | 停。列出文件名，不动手 |
| `origin` 不是自己的仓库 | 停。见上面第 ③ 档 |
| 需要 force push / 改历史 / 会丢别人的提交 | 停。这种活**一律不自动做** |
| 找不到工作日志文件 | 停，问清楚建哪个（**别自己新建一个**） |
| 分支与远端分叉（非 fast-forward） | 停。让**人来**决定 merge 还是 rebase |

其余一切（改文档、写日志、commit、push）直接做完。

---

## 只推自己的库

**这是最容易犯、后果最重的一条。**

`git remote get-url origin` 必须指向**你自己的账号或组织**。项目目录下常常混着若干**第三方仓库**（vendor 的、clone 来的）——它们有写权限，但**不是你的**。

在这类仓库里：**只能看，不能 commit、不能 push。** 当前目录疑似落在里面时，**向上找到最近的项目根再判断**。

---

## 第一步：定位

1. **仓库**：从当前目录向上找 `.git`，对照上面那张表定档
2. **项目根**：日志和项目状态文档常在**项目壳那一层**，不一定在仓库里
3. **工作日志**：按序找 `工作日志.md`、`工作记录.md`、`开发日志.md`，**含 `docs/` 子目录**。文件名不统一，**认现有的那个，不要重命名**
4. **门面文档**：`项目状态.md`（若有，它是"接手先读"那份）、`README.md`、`SPEC.md`、`方案_v*.md`

---

## 第二步：取证

取材别只靠一样：

1. **本次会话上下文** —— 用户拍过什么板、为什么、试过什么不行。**这是日志里最值钱、git 里查不到的部分**
2. `git status --porcelain` + `git diff` + `git log --format="%h %s" -12`
3. **项目内的过程文件**（进度记录之类，常在 `.gitignore` 里但可读）

---

## 第三步：自检（认项目既有方式，**别新发明一套**）

**先看项目里已经有什么，跑那个**：

| 特征 | 跑什么 |
|---|---|
| `Cargo.toml` | `cargo test` |
| `package.json` 有 test 脚本 | `npm test` |
| `pyproject.toml` / `pytest.ini` | `pytest` |
| `Makefile` / `build.py` 之类 | 按项目既有方式跑 |
| 项目自带的核对脚本 | 跑它 |
| **都没有** | **跳过**，并**在汇报里写明"无自检可跑"** |

🔴 **"无自检"必须写出来，不要假装验过。** 汇报里省掉这一句，读的人会默认你验过了。

红了就停，**输出原文贴给人**。

---

## 第四步：敏感扫描（**以 `.gitignore` 为唯一事实源**）

> **第 ④ 档（没建库）直接跳过本步。** 这一步存在的唯一目的是"别把不该外发的东西推上去"；没有仓库就没有推的动作，也就没有这个风险。

**规矩由各仓库自己的 `.gitignore` 定，不另立白名单黑名单。** 所以：**信任现有 `.gitignore`，只扫它漏掉的**。

1. untracked 列表（`git status --porcelain` 的 `??` 行）里文件名命中：
   `key` / `token` / `secret` / `password` / `credential` / `凭据` / `密码` / `.env` / `.pem` / `.key` / `.p12`
2. 单个新文件 > 5MB
3. 文件内容命中下面那张表的模式
4. **仓库压根没有 `.gitignore`** → 整个 untracked 列表过一遍上面几条

命中 → **硬停列出来**。宁可停一次，不可推上去一次。

### 内容扫描的正则：**每条都必须"像真的"**

```bash
git grep -n -I -E \
  "sk-[A-Za-z0-9]{20}|ghp_[A-Za-z0-9]{36}|github_pat_[A-Za-z0-9_]{60,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY|Bearer [A-Za-z0-9_.-]{30}|password *="
```

| 模式 | 必须的尾巴长度 |
|---|---|
| `sk-…` | +20 位 |
| `ghp_…` | **+36 位** |
| `github_pat_…` | **+60 位** |
| `AKIA…` | +16 位 |
| `Bearer …` | +30 位 |
| `-----BEGIN … PRIVATE KEY` | —（这个天然就是整串） |

### ⚠️ 坑：**只写前缀，扫描器会扫到它自己**

真实踩过：某一轮扫描报工作日志命中 `ghp_` / `github_pat_`，翻了半天是**误报**——
命中的是日志里这行：

> 敏感串扫描：`ghp_` / `github_pat_` / `sk-` / `AKIA` / 私钥 / `Bearer` —— **零命中**

**记录"我扫过哪些模式"的那句话，本身就是模式名的匹配源。** 只要正则写的是光秃秃的 `ghp_`（不管后面跟什么），这条记录就会被自己抓住，**而且下一轮还会再抓一次**。

**两条规矩**：

1. **每条模式都必须带「尾巴长度」**——真 token 是 `ghp_` + 36 位乱码；文档里提到时后面跟的是反引号/空格/斜杠，长度不够，自然不报
2. **命中后先看尾巴**：前缀后面**不是**连续 token 字符（`[A-Za-z0-9_-]`）的，判**误报**，在汇报里用一行注明（"1 处误报：自己的模式名清单"），**不硬停**。只有前缀后面真跟着一长串 token 字符才走硬停

写文档提到模式名时，**顺手用反引号包起来**（`` `ghp_` ``），既好读，也天然不会命中。

---

## 第五步：写文档

### 工作日志

- **排序照该文件自己的惯例**：先读文件开头的说明，再核对最近几节的日期走向。**多数是正序、新的追加到末尾，但不是全都这样**
- **标题对齐既有格式**：`## 2026-09-16 · 简短标题` 还是 `## 2026-09-10（一）标题`，用哪个看上文
- **篇幅对齐项目既有风格**：重项目写到几百行（决策、实测数字、踩过的坑全留）；轻项目两三行。**不要把一个轻项目的日志写成重项目的样子**
- **必含**：做了什么 / 结果（**带实测数字**）/ 拍板过的决定与**为什么** / 遗留与下一步
- **只写这次真做过的。** 没跑过的别写成"已验证"；**实测数字要连版本、夹具条件一起抄——数字本身不保鲜**

### 项目状态 / README / SPEC

- 项目状态：更新顶部日期、一句话现状、待办段。它是给人 2 分钟读完的门面，**宁可短**
- README / SPEC：**只改确实过时的段落**（版本号、跑法、当前状态），**不改风格、不重构、不顺手润色**。拿不准就不动，留在汇报的遗留里

---

## 第六步：commit

> **第 ④ 档（没建库）跳过本步。** 不要顺手 `git init` 帮人建库——**建不建库是个要认真想的决定**（私密还是公开、放哪个账号、`.gitignore` 怎么写），不属于收尾该干的事。

- **风格认仓库自己的**，先采样：`git log --format="%s" -12`。是 Conventional Commits 就跟 Conventional Commits，是中文就跟中文
- 本次收尾**打包成一条** commit。信息写清**为什么**，不只写"做了什么"
- **不 amend、不 reset、不 rebase 已有提交**。历史不干净不是这次的任务
- 如果目标平台要求署名行，按该平台的要求加

---

## 第七步：push

- **没建库** → 整步跳过
- **有库但无远端** → 只 commit，汇报里注明"无远端，未推送"
- **当前分支原样推**，不切 main、不建分支
- **直连失败就挂代理重试**（代理地址按本机实际配）
- 落后远端 → 先 `git pull --ff-only` 再推；**分叉就停**（见硬停清单）
- 认证/网络仍不行 → 换一条可用的凭据通道兜底
- 🔴 **永不 force push**

---

## 第八步：结构化短报

大概十几行，能直接当周报素材：

```
✅ <项目名> · 已推送

- 文档：工作日志.md +42 行（新增一节）· README 版本号更新
- 自检：cargo test 238 passed / 0 failed
- 提交：3f1af91 feat(ui): 缩放改成自己做 + 贴边显示缩放光标
- 推送：main → origin/main（直连超时，已走代理）
- 遗留：真的拖一下 —— 这轮改的就是没人验过的路径
```

**没建库**的项目，报头写成 `✅ <项目名> · 已更新文档（未建库）`，并把"没有 git 仓库，未提交未推送"**明说一句**。

**没有自检、没有远端、没建库、跳过了某个文档，都要如实写出来，不要省略。**

---

## 常见坑

- **仓库在子目录**：在项目壳那一层跑 git 命令会报"不是仓库"
- **别人的仓库别推**：见「只推自己的库」
- **`git add -A` 是雷**：被忽略的目录（worktree、缓存、临时产物）一旦没进 `.gitignore`，整棵树会被提交进去。**提交前先看 `git status` 全貌**
- **中文路径**：某些系统下 git 把中文名显示成八进制转义，加 `-c core.quotepath=false` 可读
